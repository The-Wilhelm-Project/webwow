# Webwow – Bestandsaufnahme, Review und Upstream-Sync (September 2026)

Stand: 12.09.2026. Bezieht sich auf den Fork-Stand `09bd627` (Branch `main`, Basis ycode 0.9.0)
und den neuen Stand auf ycode 1.30.15 (Branch `claude/wyecode-review-fixes-v1pvmg`).

## 1. Was war das Ziel des Forks?

Aus README, Commit-Historie und Code lassen sich vier Ziele ablesen:

1. **Selbst hosten ohne Supabase und Vercel** – nur Docker + PostgreSQL + lokale Uploads
   (`docker compose up -d`, Port 3002). Das ist die eigentliche Existenzberechtigung des Forks.
2. **Whitelabel** – kein "Made in Ycode"-Badge, eigene Brand-Assets (Wilhelm-Icon, OG-Image,
   Manifest), Builder unter `/webwow` statt `/ycode`.
3. **Migrationsassistent** – bestehende Webflow-Sites per ZIP-Export (+ CMS-CSVs) importieren
   ("mehr so wie Webflow", "Import").
4. Kleinere Verbesserungen (kein "Loading builder data"-Flackern, MCP-Publish-Fix, größere
   Upload-Limits für ZIP-Importe).

Die Fork-Historie besteht aus 13 Commits (02.04.–29.08.2026). Der erste Commit `276890f`
("chore: fix lint-staged, gitignore and type errors") ist in Wahrheit der große Umbau: 264 Dateien,
Supabase-Entfernung, Docker, Webflow-Importer (mit Cursor erstellt). Danach folgten Whitelabel
(`51a9bfd`), der Rename `/ycode → /webwow` (`7ea882d`, ~200 Dateien), Import-Fixes (`80dbc52`,
`b9e1894`), der MCP-Fix (`48bc597`) und Brand-Assets (`09bd627`).

## 2. Warum lief es nicht (mehr) richtig?

### 2.1 Reproduktion

In dieser Umgebung (Linux, Node 22, Postgres 16) ließ sich der alte Fork **starten**: `npm ci`,
`npm run migrate:latest` (29 Migrationen), `npm run dev` und `npm run build` liefen durch, Login und
Builder funktionierten. Ein harter Start-Abbruch war also nicht reproduzierbar. Sehr wahrscheinliche
Ursachen für "es bricht immer ab" in der echten Umgebung (alle im Code belegt):

| Symptom | Ursache im alten Fork | Status jetzt |
|---|---|---|
| Docker-Login "hält nicht", Endlosschleife Login → Builder → 401 | Cookie mit `secure: NODE_ENV==='production'`; über `http://<LAN-IP>:3002` verwirft der Browser es | behoben: Secure-Flag folgt dem Request-Protokoll (`WEBWOW_SECURE_COOKIES` zum Erzwingen) |
| Erster Klick im Builder "sperrt" den Layer, nichts mehr editierbar | Lock-Owner ist eine Session-UUID, verglichen wird gegen die Konstante `'admin'` | behoben: Upstream-Code mit echten User-Objekten aus der neuen Auth |
| Bilder/Fonts/Thumbnails im Editor 404 | `getPublicUrl()` liefert `/uploads/...`, nichts liefert diesen Pfad aus | behoben: `/storage/v1/object/public/...`-Route + Fetch-Interceptor |
| Webflow-Import >10 MB bricht im Container ab | Dockerfile kopierte `next.config.ts` nicht → Body-Limit 10 MB | behoben (Dockerfile) |
| Nach dem Import verliert die Site ihr CSS beim ersten Speichern | importiertes CSS lag in `draft_css`, dem Ausgabe-Slot des Tailwind-Generators | behoben: CSS zusätzlich als `<style>` im globalen Head-Code |
| Google-Fonts-Liste leer, Sample-Collections `ENOENT` im Container | `storage/` nicht ins Image kopiert | behoben (Dockerfile) |
| `next dev` stirbt mit OOM (Turbopack) | Turbopack braucht beim ersten Kompilieren jeder API-Route 1–3 GB (transient); viele Routen hintereinander → >13 GB | dokumentiert; Produktivbetrieb nutzt `next build` + `next start` (stabil ~600 MB) |

### 2.2 Sicherheitslücken im alten Fork (alle bestätigt)

- **Auth-Bypass:** `proxy.ts` prüfte nur, *ob* ein Cookie `webwow_admin_auth` existiert, nicht die
  Signatur. `curl -b 'webwow_admin_auth=x' /webwow/api/pages` lieferte 200. Damit waren alle
  Builder-APIs (Publish, Import, Assets, MCP-Token anlegen, DB-Reset) ohne Passwort erreichbar.
- `/api/templates/*` (Template anwenden = alle Inhalte löschen; Export der ganzen DB) lag außerhalb
  des Proxy-Schutzes. Upstream hat das inzwischen gefixt.
- Kein Path-Traversal-Schutz in `lib/local-storage.ts`; Setup-Routen (`connect` = SSRF, `migrate`)
  dauerhaft öffentlich; Login ohne Rate-Limit/`timingSafeEqual`; `/dev/css-controls` öffentlich.
- `import/` (104 MB) enthält den kompletten Webflow-Export einer realen Person inkl. CMS-CSVs und
  lizenzpflichtiger Fonts – im öffentlichen Repo. **Empfehlung: entfernen (git filter-repo).**

Alle Punkte außer dem letzten sind im neuen Stand behoben (neue Auth mit HMAC-Prüfung im Proxy und
in den Routen, Upstream-Proxy-Gating, Path-Normalisierung in `lib/webwow/storage.ts`).

### 2.3 Weitere bestätigte Bugs des alten Forks

- Revert schlug nach dem ersten Publish fehl (jsonb-Arrays ohne JSON-Serialisierung in `sync-utils`).
- `closeKnexClient()` in Import/Export/Template-Apply zerstörte den prozessweiten Pool.
- In-App-Migrationslauf scheiterte auf reinem Postgres (`role "anon" does not exist`).
- `is_setup_complete` = "DB antwortet" → Migrationen wurden in der App nie nachgezogen.
- Update-Check zeigte auf `webwow/webwow` (existiert nicht) und bot "Sync fork" gegen ycode an.
- `<ycode-inline-variable>` → `<webwow-inline-variable>` umbenannt ohne Datenmigration.
- Brand-Metadata (OG-Image "Webwow – Visual Website Builder") blutete in alle Kundenseiten.
- `bulkUpdateAssets` warf NOT-NULL-Fehler; Publish-Upserts setzten `deleted_at` nicht zurück.
- Webflow-Importer: Stylesheet-Reihenfolge nie erkannt (normalize.css überschreibt), CMS-Bindung auf
  die Beispielsite hart kodiert, Multi-Image-Felder verworfen, Inline-HTML als Klartext, Import
  löscht ohne Rückfrage das gesamte Projekt.

Die Repository-/Service-Bugs sind durch die Rückkehr zum Upstream-Code erledigt. Die Importer-Punkte
bestehen weiter (siehe Abschnitt 5).

## 4. Neue Architektur: Kompatibilitätsschicht statt Rewrite

Der alte Fork hatte ~106 Upstream-Dateien umgeschrieben; jedes Update wäre ein manueller Re-Port.
Der neue Stand dreht das um: **alle Upstream-Dateien bleiben byte-identisch**, Webwow ersetzt nur die
sieben Module, über die ycode mit Supabase spricht (`lib/supabase-server.ts`, `lib/supabase-auth.ts`,
`lib/supabase-route-client.ts`, `lib/supabase-browser.ts`, `lib/credentials.ts`, `knexfile.ts`,
`proxy.ts`). Dahinter steht `lib/webwow/**`:

- `postgrest.ts` – PostgREST-kompatibler Query-Builder auf knex (Filter, embedded Resources über
  FK-Erkennung, Upserts, `single()`/PGRST116, jsonb-Serialisierung, `rpc`).
- `storage.ts` – Uploads auf Platte (`UPLOAD_DIR/assets/...`), öffentliche URLs
  `/storage/v1/object/public/...`, signierte Upload-Tokens (Presign-Flow), Range-Requests.
- `auth-server.ts` – Benutzer in `auth.users`, scrypt-Passwörter, HMAC-signierte Session-Cookies,
  Owner-Bootstrap aus `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `auth.admin.*`-API.
- `realtime.ts` – No-op-Channels (keine Live-Collaboration im Einzelserver-Betrieb).
- `fetch-intercept.ts` – macht relative Storage-URLs für Server-Code fetchbar.

Dazu zwei Webwow-Migrationen (`00000000000000_webwow_bootstrap` legt `auth`/`storage`-Schemas, Rollen
und `pgcrypto` an, damit die unveränderten Upstream-Migrationen laufen; `99999999999999_webwow_defaults`
setzt Whitelabel-Defaults), Docker-Dateien, der portierte Webflow-ZIP-Importer, ein Benutzer-CLI
(`npm run webwow:user`), `docs/UPSTREAM-SYNC.md`, `docs/ARCHITECTURE.md` und `scripts/sync-upstream.sh`.

Entscheidung: Der Builder-Pfad bleibt intern `/ycode`; `/webwow/*` wird permanent umgeleitet.
Das ist der Preis für konfliktfreie Updates (siehe Abschnitt 3).

## 5. Offene Punkte / Empfehlungen

1. **`import/` aus dem Repo entfernen** (personenbezogene Daten, 104 MB); es ist jetzt zumindest aus
   dem Docker-Build-Kontext ausgeschlossen.
2. **Webflow-ZIP-Importer verbessern** (Fork-eigener Code, nicht Upstream): Stylesheet-Reihenfolge,
   CMS-Zuordnung konfigurierbar statt hart kodiert, Multi-Image-Felder, HTML→Rich-Text, Rückfrage
   vor dem Truncate. Mittelfristig auf die Upstream-Import-Pipeline (`lib/import/*`) aufsetzen, damit
   CSS→Tailwind-Übersetzung und Komponentisierung wiederverwendet werden.
3. **E-Mail-Einladungen** gibt es in Webwow nicht; Benutzer werden per `npm run webwow:user` angelegt.
   Optional: SMTP-basierte Einladung im Webwow-Layer nachrüsten.
4. **Realtime/Presence** bleibt aus (kein Live-Cursor, MCP-Änderungen erfordern Reload im Builder).
5. Dev-Modus: Turbopack braucht viel RAM beim ersten Kompilieren; auf kleinen Maschinen
   `npm run dev:webpack` verwenden oder Routen nacheinander aufrufen.
6. Beim nächsten Upstream-Release `npm run sync:upstream` verwenden und die Checkliste in
   `docs/UPSTREAM-SYNC.md` abarbeiten (neue Supabase-API-Nutzung → Shim erweitern; neue Migrationen mit
   `auth.`/`storage.`-Bezug → Bootstrap erweitern).
